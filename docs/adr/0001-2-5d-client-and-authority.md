# ADR-0001：2.5D 客户端与服务端权威模型

- 状态：已接受
- 日期：2026-08-08
- 决策者：项目发起人、架构维护者
- 关联：`ARCHITECTURE.md`、`GAME_DESIGN.md`

## 背景

早期文档把游戏描述为多人 3D Web 游戏，并提出 Three.js + Socket.IO，但没有明确客户端和服务端谁判定游戏结果。项目发起人随后明确游戏采用 2.5D。继续使用自由 3D 管线会增加素材、物理、网络同步和社区扩展成本；继续自研通用 Socket.IO 房间层也会扩大基础设施代码。

## 决策

- 产品采用固定斜俯视/正交相机的 2.5D 表现。
- 权威模拟使用二维 `x, y` 坐标、二维碰撞和固定 tick；伪高度仅用于受控表现/规则。
- Web 使用 React + Vite 作为页面壳，Phaser 作为唯一游戏渲染/输入引擎，Tiled JSON 作为地图源格式。
- Node.js + Colyseus 管理权威房间、同步、匹配和重连。
- 客户端只提交输入/动作意图，位置、伤害、奖励、背包和冷却由服务端判定。
- 首发为大厅 + 最多 16 人的独立房间，不建设无缝 MMO。

## 备选方案

### Three.js 正交相机

能呈现真正 3D 场景与固定相机，但 Tilemap、精灵动画、音频、输入、深度排序和编辑器数据需要更多自建集成。若未来美术原型证明 Phaser 无法实现目标，可通过新 ADR 复审。

### PixiJS

2D 渲染能力强、控制精细，但作为较底层 renderer，仍需组装更多游戏循环和地图能力。当前优先减少基础设施维护。

### Socket.IO 自研房间层

通用且成熟，但需要自行设计权威状态、房间、匹配、重连、同步 schema 和负载工具。Colyseus 更贴合当前需求。

## 后果

### 正面

- 服务器规则可在无浏览器环境确定性测试。
- 地图、技能、怪物和物品更容易数据化贡献。
- 客户端资源和网络状态比自由 3D 更易控制。
- 多人房间基础能力不必从 Socket.IO 原语重复建设。

### 代价与风险

- 美术必须适配固定视角、方向动画、脚点和深度排序。
- Phaser 等距 Tilemap 的具体遮挡/碰撞工作流仍需 M0 原型验证。
- 不能直接加入依赖完整 3D 物理或自由相机的玩法。
- Colyseus 是关键框架依赖，升级需要协议和重连回归测试。

## 验证与回退

M0 必须制作一张小型等距地图原型，验证角色八/四方向移动、深度排序、遮挡、碰撞、相机缩放和中低端设备帧率。M1 必须验证 16 个模拟客户端下的 tick 与带宽基线。

若原型未达标，先比较 Phaser 正交地图、PixiJS 和 Three.js 正交相机的同素材小样，再用新 ADR 取代本文。不得在产品代码中同时维护两套引擎作为“临时方案”。
